# Known limitations at v1.0.0

One row per finding of the [architecture review](architecture-review.md), R1–R12, with the decision taken for v1.0.0: `fixed in v1.0.0` or `accepted for v1.0.0`. "Fixed" means the change ships in v1.0.0 itself; "accepted" means the behaviour is documented and a consumer or operator can work around it.

| # | Finding (one line) | Status | Reason | What to do meanwhile |
|---|---|---|---|---|
| R1 | Telemetry privacy not established (Sentry captures URLs, headers, exception text) | accepted for v1.0.0 | No sanitiser is shipped; a config-cache-compatible one needs its own tests | Leave `SENTRY_LARAVEL_DSN` unset (the default); rely on the application log — its `api.request` line records the route name, never the path; exception reports still carry the exception message, so treat the log as sensitive |
| R2 | MariaDB 10.5 is past community maintenance | fixed in v1.0.0 for CI; accepted for v1.0.0 (hosting) | Both 10.5 and 10.11 are required CI legs (ADR 0001, amended); the shared-hosting target's actual MariaDB version is the owner's decision | Run 10.11 where you can choose; the schema needs nothing newer than 10.5 |
| R3 | A variant groups EEA observations by a coarse tuple; attribute values come from the last-imported row | accepted for v1.0.0 | Changing identity semantics needs an ADR and a data migration; ids and provenance stay stable | Treat `specifications`, `mass_kg` and `co2_wltp` as representative values of the group, not a homologated configuration; `sources[]` (key `eea`) gives licence, attribution and `retrieved_at`, not a dataset year — `year_from` is the earliest reporting year merged into this variant, not the year of the values shown; no field names the year of the observation those values come from |
| R4 | The importer fetches the network inside the write transaction; a killed process can leave a run `running` | accepted for v1.0.0 | Full-size import timing has not been measured; staging is a design in itself | Run one `vehicle:import` at a time, by hand or by the scheduler; check the `vd_import_runs` table directly for a stale `running` row — `vehicle:status` does not surface it |
| R5 | `updated_since` covers row timestamps, not representation changes (a make rename does not touch its models) | accepted for v1.0.0 | A publication revision / change ledger is a v1.1 design | Take a full snapshot (`/v1/snapshots/…`) weekly and use `updated_since` only between snapshots |
| R6 | A manufacturer's cached `parent` slug can go stale | accepted for v1.0.0 | Coupled to R5 | Resolve `parent` through `/v1/manufacturers/{key}`, which follows renames; note that `parent_slug` is set only when an active parent link matches (`ManufacturerWriter::finish()`'s join) — if the upstream parent link is removed, the cached `parent` can still name the former parent indefinitely |
| R7 | ETags claimed strong semantics | fixed in v1.0.0 | Weak validators, RFC 9110 conditional handling | — |
| R8 | Deployment is not gated on the exact commit's checks | accepted for v1.0.0 | This repository's own deploy job never runs (no `DEPLOY_HOST` secret here); a platform calling the reusable `deploy.yml` via `workflow_call` triggers `deploy` gated only on secret presence and any `production` environment rules the caller sets, not on this repository's `ci` checks for that commit | Deploy only a tag whose `ci` run, including `release-check`, is green. |
| R9 | Snapshots are streamed queries, not consistent artefacts | accepted for v1.0.0 | The catalogue is small; an import during a download can interleave | Count checks work only for manufacturers and makes, using `meta.total` on their flat list routes (`/v1/makes` defaults to `kind=car`; the snapshot applies no kind filter); models and variants have no flat list route to total against. Re-download if an import finished mid-download: check `/v1/health/ready`'s `imports` timestamps (keyed) or `vehicle:status` (operator) before and after |
| R10 | Extension contracts are narrower than described | accepted for v1.0.0 | `VariantWriter::write()` and `FleetWriter::write()` hard-code the `car` kind, so a registered second kind gets a schema and a contract fragment but no core writer can import it, and writers are fixed in `CoreServiceProvider` at v1.0.0; importing a second kind needs a core change (see `docs/platform-bootstrap.md`) | Never re-register `car`; `KindRegistry::register()` replaces a duplicate silently, so use unique kind names |
| R11 | Daily p95 loaded every duration into memory | fixed in v1.0.0 (daily p95); the rest accepted for v1.0.0 | Still open: the WMI reject allowance of 1.0 (`CORE_IMPORT_REJECT_SHARE_WMI`, `config/core.php`) can pass a fully-rejected feed as a successful run; `LimitBodySize` checks only the declared `Content-Length`; `RecordUsage`'s `bytes` is not the actual download size for streamed responses (snapshots); no bounded retention for raw artifacts or reject samples | After a `wmi` import, check its row counts instead of trusting the run status alone: `php artisan vehicle:status` lists `rows written` and `rejected` for each source's last successful run (the full reject report is in that run's `vd_import_runs.reject_report`). The fixture baseline is 200 rows read, 182 written, 18 rejected (9 %, all `wmi_length`); a real vPIC feed's share differs, but a run whose rejects approach its rows read means a broken feed. vPIC's 6-character WMIs are rejected by design, so a `wmi` run's reject share is legitimately high, and tightening `CORE_IMPORT_REJECT_SHARE_WMI` risks aborting a normal import instead of catching a bad one; enforce request body size and rate limits at the web server/edge, not only in the app |
| R12 | Licence policy was checked only at release time | fixed in v1.0.0 (licence before import); the rest accepted for v1.0.0 | Still open: `oasdiff` in CI compares only the base `openapi.yaml`, not the runtime-assembled contract with kind fragments; the `breaking` PR label skips that check with no automated major-version/`/v2` guard | Use the `breaking` label only before the first release, or alongside an actual new major version/`/v2` path — treat it as review metadata, not proof of compatibility |
